# 0.3.5 phone-debugging update

Fixed a reconnect loop observed on the Android 13 test phone: Android reports
the VPN network as its owner's default even when that app is not in the VPN
allowlist. Monitoring the default network therefore halted the packet pump as
soon as MeshHome established its own VPN. The earlier UI could still show the
native peer as connected after that pump had stopped.

`Networks.Monitor` now subscribes explicitly to INTERNET + NOT_VPN networks,
keeps callback-provided properties, and invalidates a session only when its
selected physical binding changes or becomes unavailable/blocked. It prefers
the physical default when available, otherwise a validated physical network
(Wi-Fi preferred at equal validation). One-shot account network selection also
handles the VPN-owner default-network case. Every transport/DNS socket remains
protected and explicitly bound, and Wi-Fi-only eligibility is still enforced.

The controller recreates a stopped pump even if the routing fingerprint did
not change, and refuses to publish healthy status for a stopped pump. Service
dump diagnostics contain aggregate packet/DNS counters and a bounded physical
network event history, not tokens, private keys, or query history.

Phone observations after installing 0.3.5 and tapping Connect:

- Android reports an active VPN interface, DNS server 198.18.0.1, and the
  selected app UIDs. The selected peer connects; packet pump remains running.
- Opening a test wildcard subdomain in Brave resulted in 3 DNS requests and
  3 DNS responses with zero DNS failures, plus outbound Meshnet packets.
- Successful web-service responses have NOT yet been confirmed. Neither these
  observations nor the JVM tests establish complete end-to-end reachability,
  transition/leak safety, or battery performance.

Android assembly, test-APK compilation, 55 JVM tests, and lint passed for this
build. The updated packet-pump instrumentation tests have not yet been run on
the phone. See `0.3.2.md` for the replacement filter and its restrictions.
