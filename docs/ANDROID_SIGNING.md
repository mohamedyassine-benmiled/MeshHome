# Persistent Android app signing

The Android application ID is `com.mybm.meshhome`. Android will only install an
APK as an in-place update when **both** the application ID and signing
certificate match the installed app. A GitHub-hosted runner's autogenerated
debug key is not stable and must not be used for distributable updates.

The workflow `.github/workflows/signed-apk.yml` uses a persistent upload
keystore and builds the pinned native engine before creating a signed arm64
release APK. A manual `workflow_dispatch` run uploads a short-lived Actions
artifact only. Pushing a semantic-version tag such as `v0.4.0` runs tests and
automatically creates a **published GitHub Release** containing the APK,
SHA-256 sums, MeshHome source archive, pinned libtelio source archive and the
Android adapter patch. The release version name follows the tag; Android's
version code increases with the workflow run number.

The workflow requires four **repository Actions secrets** (not ordinary
repository variables):

| Secret name | Value |
|---|---|
| `MESH_HOME_KEYSTORE_BASE64` | Base64-encoded bytes of the JKS/PKCS12 keystore |
| `MESH_HOME_KEYSTORE_PASSWORD` | Keystore password |
| `MESH_HOME_KEY_ALIAS` | Alias of the signing key |
| `MESH_HOME_KEY_PASSWORD` | Private-key password |

## Create a new signing key

Do this once on a trusted machine, not in GitHub Actions. Keep multiple secure
offline backups of the keystore and passwords. **If the private key is lost,
future APKs cannot update installations signed with it.** Do not commit either
the keystore or its base64 encoding.

```sh
keytool -genkeypair -v -keystore meshhome-upload.jks -alias meshhome \
  -keyalg RSA -keysize 4096 -validity 10000
```

Choose a strong unique password for the keystore and key. Then base64-encode the
binary keystore and add the four values under:

**GitHub repository → Settings → Secrets and variables → Actions → New repository secret**

PowerShell:

```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes("meshhome-upload.jks")) |
  Set-Content -NoNewline meshhome-upload.base64
```

macOS/Linux:

```sh
base64 < meshhome-upload.jks | tr -d '\n' > meshhome-upload.base64
```

Paste the encoded contents as `MESH_HOME_KEYSTORE_BASE64`; add the alias and
passwords as their respective secrets. Keep the temporary `.base64` file outside
the repository and delete it after setting the secret. GitHub masks configured
secret values in workflow logs; never print or echo them.

## Build and install

After all four repository secrets are configured, use **Actions → Android signed
build and release → Run workflow** to test a signed build without publishing a
release. To publish, push a `vMAJOR.MINOR.PATCH` tag to the repository; that
tagged commit is built and published automatically. Protect the `v*` tag
pattern with a GitHub ruleset so only trusted maintainers can create release
tags. Only tag commits that have passed device/security review and are ready for
public distribution.

The workflow attaches the pinned libtelio source and integration patch, but the
repository's third-party license inventory is explicitly incomplete. Do not
start public versioned releases until all required dependency notices/source
materials have been reviewed and assembled. Build success alone does not make
the release legally or operationally production-ready.

The currently sideloaded development installation used an earlier application
ID; Android treats `com.mybm.meshhome` as a separate app. Its data will not
migrate automatically. The new signing key also cannot update builds signed
with a different certificate. Test a clean install and retain access to the
previous build before removing any existing app/data.

If the initial install must update a debug-signed `com.mybm.meshhome` build,
the new persistent key will not match Android's debug certificate. Uninstalling
that build (and its app data) before installing the first persistent-key APK is
normally required. Back up any needed account recovery information first; never
export or share the Nord token as part of this process.

Debug builds continue to use Android's local debug key. Release builds fail
unless all four signing values are supplied as environment variables; see
`app/build.gradle.kts` for the supported variable names.
